# 要求ログ（2026-11-14）

何が起きたかを後から追うための記録。2026-11-14 に D1 の過負荷（`D1 DB is overloaded`）で 502 が出たとき、どの要求が重なっていたかがどこにも残っておらず、原因を特定できなかったので入れた。

## 2 段で残す

| 段 | 何を | どこに | 保持 |
|---|---|---|---|
| 1 | 全要求を 1 行の JSON（`{"kairos":"req",method,route,status,ms,src}`）。失敗は本文の先頭 300 字を足した `{"kairos":"err",…}` も | `console.log` → Cloudflare の Workers Logs（`wrangler.toml` の `[observability]`） | Cloudflare 側の保持期間で自動的に入れ替わる |
| 2 | 失敗（5xx）と遅い要求（3 秒以上）だけ | D1 の `req_log`（ts・method・route・status・ms・src・err） | 30 日。書くたびに古い行を捨てる |

全要求を D1 に書かないのは、記録そのものが D1 の負荷になるため。1 段目は D1 を使わない。

- `route` はパスの ID を `:id` に丸めたもの。クエリ文字列（`note=` などの本文）は残さない。
- `src` は `http`（画面・外部からの要求）か `mcp`（MCP の道具が中で呼んだ API）。MCP の失敗は道具のエラー文になって外側の `/mcp` は 200 で返るので、中の呼び出しを別に拾っている。
- D1 が過負荷で落ちた要求は、記録の書き込みも同じ理由で落ちる。12 秒待って 1 回だけやり直す。それでも落ちたら 1 段目にだけ残る。
- 記録は補助。失敗しても応答は変えない。`ctx.waitUntil` で応答の後に書く。

## 読む

```
GET /api/reqlog?days=1&limit=200
```

`routes` が道ごとの件数・失敗数・最大所要時間・最後に出た時刻、`rows` が新しい順の生の行。`days` は 90 まで、`limit` は 1000 まで。

## 変えられる値（vars）

| 名前 | 既定 | 意味 |
|---|---|---|
| `REQLOG_SLOW_MS` | 3000 | これ以上かかった要求を D1 に残す |
| `REQLOG_KEEP_DAYS` | 30 | D1 に残す日数 |
