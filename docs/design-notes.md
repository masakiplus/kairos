# 設計の経緯（なぜこうなっているか）

時系列で、採った判断と捨てた案を残す。詳細な振る舞いは `rules.md`、スキーマは `notion-schema.md`。

## 出発点（2026-09-27）

- Notion ✅ Tasks を正本にしたあと、**スマホから 1 タップで回す層が無かった**。Notion アプリは一覧→開く→プロパティ→保存 で 4 タップ、しかも内蔵ブラウザから AI チャットのリンクがネイティブアプリに飛ばない。
- 候補: (a) Notion のビューと式列だけで我慢、(b) ネイティブアプリ、(c) Cloudflare Worker 1 本の PWA。
- (a) は同日中に撤回（タップ数が減らない）。(b) はストア配布・更新の重さで却下。**(c) を採用**: Worker が静的な画面と Notion を叩く API を両方配る。ホーム画面から開く。Android は `intent://` で AI アプリを直接起動できる。
- 名前は 2 日後に **Kairos**（καιρός＝機が熟した時）。執務側のタスク環境を Chronos（流れて積もる時）と呼んで対にした。

## 設計原則

1. **人＝判断、AI＝実行、Notion＝記録。** Kairos は判断を押す場であって、考える場ではない。
2. **規約のロジックは Worker に一本化。** 画面は表示と 1 タップ。他のツール（夜間棚卸し・対話スキル）と挙動がずれないように、完了 3 点セット・延期は開始日・アイコン必須 などを Worker が守る。
3. **列を増やさない。** 「今夜」は開始日の時刻で、「待ちの相手」は説明欄の先頭行で、「見送り」は完了＋説明の根拠行で表す。増やしたのは `今日の3つ`（date）、`AI処理開始／種別／セッション`、`担当` くらい。
4. **自動で結ばない・自動で消さない。** 依存・日程・クローズは必ず人が確定する。機械が書くのは提案と印だけ。
5. **公開前に検査。** 構文エラーのまま公開して画面が止まった事故（2026-09-29）から、ESM は `.mjs` に写して `node --check`、gitleaks、版数のバンプを手順に固定した。

## 画面の構成

- タブ: 今日やる／今日できる／スマホで／PJ別／役割／見直し／委任。横スクロール。
- 行: 丸タップ＝完了、右スワイプ＝🤖、左スワイプ＝明日へ、タップ＝シート。
- シート: 概要 → 🚦 状態 → ⏭ 先行 → 🤖 AI → 📅 日程 → 👥 委任 → 🔗 Notion → ✅ 片付ける（完了を一番下。開いたからには何かする前提）。前後のタスクへ ‹ › で移動。
- 見た目は Things 風（淡いグレー地・白カード・青アクセント・丸チェック）。自動／ライト／ダーク。

## やらないと決めたこと

- タスクの編集画面（それは AI の仕事）
- Roles / Projects の編集画面
- ネイティブアプリ化、通知常駐
- 自動で依存を結ぶ・自動でタスクを消す

## 他環境へ寄せるときの要点

- フィールドの対応・差分の作業リスト・受け入れ確認は `chronos-sync.md` にまとめた。
- まず `rules.md` の §2（完了 3 点セット）・§3（延期は開始日）・§5（依存は人が結ぶ）を合わせる。ここがずれると棚卸しが互いの変更を「異常」と見なす。
- 一覧の条件（§4）は Notion の式列を正とし、画面側は同じ判定を素の日付で重ねる。式列の定義は `notion-schema.md`。
- Kairos の API は REST（`GET /api/tasks?view=`、`POST /api/tasks/:id/<action>` …）。別フロントエンドから同じ Worker を叩く設計もできる。
